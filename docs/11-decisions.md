# 11 — Architecture decision register (ADRs)

| ADR | Choice | Rejected / deferred | Rationale | Review trigger |
|---|---|---|---|---|
| ADR-001 | One TypeScript monorepo with npm workspaces | Split frontend/backend repos | Shared contracts, fewer integration points | Team expands substantially |
| ADR-002 | React/Vite SPA | Next.js SSR | Workspace interaction dominates, simplify deployment | SEO/SSR becomes product requirement |
| ADR-003 | Modular monolith API Lambda + separate runner | Distributed microservices | Lower IAM/deploy overhead | Heavy independent workloads |
| ADR-004 | DynamoDB + S3 | Supabase/Postgres for MVP | Demonstrate AWS-native persistence | Relational complexity or enterprise analytics justify change |
| ADR-005 | AWS SAM infrastructure | Ad hoc console-only or sprawling Terraform modules | Reproducibility and explainability | Event IAM permissions block SAM |
| ADR-006 | Cognito + backend membership authorization | Global app role; frontend role switch | True identity and org-scoped permissions | Account restrictions require demo fallback |
| ADR-007 | Pure deterministic scenario engine | LLM as source of truth | Repeatability, testability, safety | None, core invariant |
| ADR-008 | Simulated app adapters + real bounded AWS runner | Full desktop/GitHub/Jira clones | Complete product path in 22 hours | Post-hackathon dedicated sandbox requirement |
| ADR-009 | Evidence-first manager review | Video-only AI scoring | Revision/test traceability, less invasive | User research shows visual replay necessary |
| ADR-010 | Bedrock review draft, then coworker | Multi-agent orchestration/fine-tuning | Concrete AI value with limited complexity | Validated labeled data, workload complexity |
| ADR-011 | Human final review | AI autonomous employment decision | Employment stakes and evidence uncertainty | Do not automate without independent validation/legal review |
| ADR-012 | One credible incident | Many thin scenarios | Completeness is more important than catalog | Golden path works ahead of schedule |
| ADR-013 | OnboardOS as temporary working brand | Commercial exclusive-name claim | Existing commercial name use found | Naming and trademark due diligence |
| ADR-014 | On-demand test execution with revision hash | UI generated fake success | Real AWS technical proof | Any implementation that cannot preserve exact revision |
| ADR-015 | 2026-11-07: Deterministic assignment/session ids (SHA-256 of org + scenario version + employee) with conditional writes | Random ids plus an idempotency-key ledger | Retries and double-clicks are idempotent by construction with no extra table; ids are opaque and are never a security control (every read re-checks ownership) | Multiple concurrent attempts per employee/scenario are needed |
| ADR-016 | 2026-11-07: `GSI2` holds a manager's assignments under sort-key prefix `ASSIGN#`; `REVIEWABLE#` stays reserved in the same partition | A third GSI; scanning | Uses the frozen index without a schema change; the review slice moves an item's `GSI2SK` to `REVIEWABLE#` when it becomes reviewable | Review-queue and assignment-list access patterns collide |
| ADR-017 | 2026-11-07: Manager read-only session preview deferred; manager/admin assignment lists show only assignments they created | Org-wide listing now | Org-wide listing needs an org-keyed index or a scan; neither is justified for the demo | Managers need to see their team's work without having created it |
| ADR-018 | 2026-11-07: Added `GET /v1/orgs/:orgId/assignable-employees` (single-partition Query on `ORG#<org>`) | Client-supplied employee ids found out-of-band | A manager needs to choose an assignee; the route returns only `userSub`, display name and teams, scoped by the server | Org size makes a bounded single-partition Query unsuitable |
| ADR-019 | 2026-11-07: Scenario content is served only by the API; `packages/scenario-fixtures` is server-only and the web app must not import it | Bundling fixtures into the SPA | Invariant 5: nothing hidden, and no synchronized-screen fakes; enforced by a source-boundary test and a bundle check | None |
| ADR-020 | 2026-11-07: Baseline config is "revision 0" taken from the scenario; only saved revisions (1..N) are stored items. Each test run embeds its own immutable snapshot | Materialising revision 0 in the start transaction | Live Phase 2B sessions have no revision items and the start transaction stays unchanged; a run is self-describing | Evidence must reference a stored baseline item |
| ADR-021 | 2026-11-07: Test-run item key is `TEST#<runId>` with `runId = run_<4-digit n>_<12 hex>` (deterministic from session + n), not `TEST#<createdAt>#<id>` as sketched in doc 04 | Timestamp-prefixed key | A run is fetched by id with a consistent `GetItem`; ordering is kept because `n` is zero-padded; concurrent requests for the same slot collide on one id | A listing by time across sessions is needed |
| ADR-022 | 2026-11-07: Runner outcomes enter the session only via a system-only engine action (`RECORD_TEST_RESULT`, actor `system:scenario-runner`); client actions can never use that actor and no route accepts the action | Letting the route write run status directly | Keeps "one authoritative owner of state": every status change has a versioned event and passes the same reducer; a forged result is unrepresentable on the client path | None |
| ADR-023 | 2026-11-07: Staleness/currentness is derived at read time from (revision, hash, suite version) | Stored `stale` flag updated on save | History is never rewritten; there is no second place that can disagree | Query patterns need to filter on staleness |
| ADR-024 | 2026-11-07: Runner request/response schemas live in the server-only scenario-engine package | Put them in `contracts` | `contracts` is bundled into the browser; the protocol includes snapshots/ids the browser must not depend on | The browser must render raw runner payloads |
| ADR-025 | 2026-11-07: Synchronous `RequestResponse` invoke from the API with a 15 s abort, PENDING persisted first, stranded-run repair on poll | Step Functions / queue / async invoke + callback | Smallest mechanism that satisfies the frozen protocol and is honest about failure; no new services | Runs exceed the API timeout or volume grows |
| ADR-026 | 2026-11-07: Employees see `executor` request ids, not the runner's name/ARN; results carry no thresholds | Showing the suite or function identity | Request ids let a reviewer find the log line without disclosing infrastructure or the hidden suite | Managers need richer provenance |
| ADR-027 | 2026-11-07: A submission id encodes its assignment and attempt (`sub_<NN>_<assignment hex>`); submissions and their single decision live at `ASSIGN#<id>/SUBMISSION#<NN>` and `DECISION#<NN>` (not `SESSION#id/SUBMISSION#n` / `SUBMISSION#id/REVIEW#id` as in docs 04 and 14) | A random submission id with a lookup index; a new GSI | `GET /v1/reviews/{id}` is a consistent key lookup with no scan and no index; history of all attempts is one partition Query; create-if-absent on a fixed slot makes immutability and "one decision" structural | Review needs to look up by something other than submission id |
| ADR-028 | 2026-11-07: Without AI, submit moves the assignment `IN_PROGRESS -> AWAITING_REVIEW` in one transaction with `evaluation = NOT_CONFIGURED`; `SUBMITTED`/`EVALUATING` reserved | A two-step `SUBMITTED -> AWAITING_REVIEW` | A second write is non-atomic and can strand a submission invisible to managers; the explicit NOT_CONFIGURED state is honest and keeps the Bedrock transition additive | Bedrock evaluation lands |
| ADR-029 | 2026-11-07: Manager queue = existing `GSI2` `ASSIGN#` listing filtered by status, with `latestSubmissionId` on the assignment; the reserved `REVIEWABLE#` prefix stays unused | Moving `GSI2SK` to `REVIEWABLE#` on submit; scanning | Does not break the assignment listing, needs no new index; the cost is eventual consistency and the 50-item page | Managers have many assignments, or the queue must be strongly consistent |
| ADR-030 | 2026-11-07: A revision begins as a new session on the same assignment (`sessionIdFor(assignmentId, N+1)`), started by the employee; assignment stays `REVISION_REQUESTED` until then; max 5 attempts | Rewinding the old session; re-assigning (new assignment id); returning to `IN_PROGRESS` at decision time | Old evidence is never touched; no change to assignment identity; nobody has to create a session on the manager's behalf; the freeze doc's "returns to IN_PROGRESS" is satisfied when the employee begins | Per-employee multiple concurrent attempts are needed |
| ADR-031 | 2026-11-07: The review decision is an engine action (`RECORD_REVIEW`) that bumps the submitted session's `stateVersion` and emits `REVIEW_DECIDED`; the engine refuses the employee and the system identity as reviewer | Writing the decision outside the reducer | Keeps "event sequence == state version" for every change; self-review is unrepresentable; a second layer behind the create-only decision slot | None |
| ADR-032 | 2026-11-07: Submission requests carry an assertion of the evidence (run id, revision, hash) and a required `Idempotency-Key`; the server derives the evidence and compares | Trusting client ids; selecting evidence from the client's choice | Stale, forged and cross-session evidence are rejected with no way for the client to select what is frozen; the persistent ledger gives replay safety beyond DynamoDB's 10-minute token window | None |
| ADR-033 | 2026-11-07: API role gains `dynamodb:Query` on the Events table ARN only, for the evidence timeline | Duplicating events into Core; granting Get/Scan | The Events table stays the single authoritative event source; the grant is one bounded single-partition action on one table with no indexes | Timeline moves to a precomputed artifact |
| ADR-034 | 2026-11-07: The AI coworker is a server-side Amazon Bedrock Converse call (`amazon.nova-micro-v1:0`, invoked directly on demand in `us-east-1`; no inference profile) behind a `BedrockProvider` interface, with no tools, text-only output, one SDK attempt and a 20 s abort | Browser-side calls; an agent with tools; a cross-region profile | The model can only produce words, so a manipulated model cannot mutate state, tests, submissions or reviews; a direct model ARN keeps IAM to one action on one resource and the data in-region; one attempt means no hidden repeat billing | A feature needs the model to act on the user's behalf |
| ADR-035 | 2026-11-07: Chat turns are NOT scenario state: they live under `SESSION#id` in the Core table as `CHAT#CTL` / `CHAT#MSG#<turnId>` / `CHAT#IDEM#<key>`, never touch the `STATE` item, bump no `stateVersion` and write no Events rows | Routing chat through the reducer as actions; a new table | Keeps "event sequence == state version" exact and the 200-action cap unaffected; no change to submissions. Consequence: chat is not in the frozen evidence manifest | Managers need chat in the evidence (see below) |
| ADR-036 | 2026-11-07: Exactly one paid call per reservation: a `CHAT#CTL` control item with a revision counter is changed only by a conditional TransactWriteItems that also creates the PENDING turn and the idempotency ledger entry and `ConditionCheck`s the STATE item (still INVESTIGATING, still this employee); the model is called only after that transaction commits, completion releases the lock only if it still owns it, and a 60 s lease lets a later request or read close an abandoned turn as STRANDED | A count-based lock read before writing; a deterministic count-derived slot id | A read-then-count lock lets concurrent requests all pass; the revision condition makes lock acquisition, counters and the new turn one atomic decision. Cost: `dynamodb:ConditionCheckItem` on the Core table (granted only when the coworker is enabled) | A queue or Step Functions becomes justified |
| ADR-037 | 2026-11-07: The coworker is OFF unless `CoworkerModelId` is set. The parameter accepts only empty or `amazon.nova-micro-v1:0`, the Bedrock IAM policy is created only when it is non-empty, and the API then reports `enabled:false` instead of simulating answers | Always-on with a default model; a free-text model parameter | Deploying the infrastructure changes nothing observable until the feature is deliberately switched on, and the IAM resource can never become a wildcard or an unreviewed model | The feature is promoted to always-on |
| ADR-038 | 2026-11-07: Future manager-visible AI-assistance evidence will be an additive, optional field on NEW frozen submissions (counts, model id, first/last timestamps and a SHA-256 digest of the ordered turns), not the transcript; old submissions read as "not recorded" | Embedding transcripts; retrofitting existing submissions | Managers learn that and how much AI help was used without exposing private conversation text; the digest lets a later, explicit disclosure be verified against what was frozen; model text stays non-authoritative | A decision to show transcripts to managers |
| ADR-039 | 2026-11-08: Coworker prompt v2 is data-driven. A strict, size-bounded `ScenarioCoachingProfile` (types in `contracts`, validator and defaults in `services/api`, built-in data in `scenario-fixtures`, looked up by scenario version and NOT a field of `PublishedScenario`) feeds a generic rule set that only chooses sentences from closed enums; historical records, live state and test results are labelled apart; the newest answer is never shortened and the oldest exchanges drop first with an announcement. Built-in profiles are platform-versioned (id, version, pinned hash, recorded on every turn), not frozen per assignment; an invalid profile falls back to defaults with a logged, recorded source | Incident-specific prompt strings; a free-form manager system prompt; keyword rules; putting the profile inside the immutable scenario version; a runtime schema in `contracts` | Fixes the two observed failures at their cause without hardcoding INC-104, is honest about what a deployment can change, and keeps the private runner artifact byte-identical | `contracts` (types only), `API` (context builder, validator; no route/IAM/template change), `scenario-fixtures` (+registry; `INC_104_V1` unchanged), `tests`; API-only Lambda bundle change, runner and smoke bundles verified identical; see docs/ai-coworker-architecture.md |

| ADR-040 | 2026-11-08: Organization coaching is three record types in the existing Core table under `ORG#<org>`: one editable revisioned draft per (scenario, scenario version), immutable published versions, and a current-version pointer. Publish is one `TransactWriteItems` (create version if absent + compare-and-set the pointer on the previous version + stamp the draft only if still at the published revision); a draft save is a conditional write on its revision. Profile version and scenario version are separate numbers; the profile id is a stable hash of org + scenario | A new table; storing coaching inside the scenario definition; `ConditionCheckItem` for the draft check; last-writer-wins drafts | Needs no new table, index or IAM action, makes every published version write-once, and turns stale editors and racing publishers into 409s rather than overwrites | `contracts` (+coachingStudio.ts), `API` (6 routes), `template.yaml` (6 routes), tests; the draft/published schemas are validated on every read |
| ADR-041 | 2026-11-08: An assignment is bound to the organization-published coaching version that was current when it was created (`coachingRef` with profile id, version and content hash), written once in the same conditional Put that creates it. The coaching version is NOT part of the deterministic assignment id. At runtime the exact referenced version is loaded and verified (shape, organization, scenario, identity, hash); any failure refuses the question with `503 COACHING_UNAVAILABLE` and a structured log, and is never replaced by the newest version, built-in coaching or another organization's data. Assignments without a reference keep the platform's built-in coaching. A replay of an assignment request first looks the assignment up by its deterministic id and returns it as it is, reading no coaching records, so a moved, missing or corrupt pointer cannot fail a valid existing assignment; an explicit request for different coaching on an existing assignment is `409 COACHING_MISMATCH` | Putting the version in the assignment id (publishing would mint assignments and reset progress); resolving "latest" at question time; silent fallback on failure | Publishing must not change running work, and a policy that cannot be verified must not be quietly swapped for a different one | `records.ts`, `routes/assignments.ts`, `routes/coworker.ts`, `coachingRuntime.ts`; legacy assignments and sessions untouched |

Record changes with date, owner, reason, and impact on `contracts`, `API`, `tests`, `deployment` so agents do not silently diverge.
